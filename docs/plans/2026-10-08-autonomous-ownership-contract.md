# Autonomous ownership contract

Unit: MICROKERNEL-OWNERSHIP. Design baseline: HEAD `b6b714c`, authorized branch `feat/monster-hp-d8`. Status: proposed contract; no implementation, proof completion, runtime acceptance or goal closure is claimed.

This strengthens S1/S3/S6/S7 and A1–A7 of the [microkernel goal](2026-10-08-microkernel-goal.md). Autonomous objects own and maintain authoritative state, module behavior and live extension bindings. These are in-process ownership boundaries, not network microservices. A shared property database with owner labels does not satisfy this contract.

## Baseline and boundary

The [resource contract](2026-10-08-resource-service-contract.md) and [resource README](../../crates/nethacked-resources/README.md) describe `Service(Rc<RefCell<Inner>>)` with one `State.resources: BTreeMap<Resource, Snapshot>`. `OwnerPolicy` binds permissions and validators; it does not hold independent authoritative state or command behavior. That centralized service **does not meet autonomous ownership**. Its authority, refusal and accounting fixtures remain reusable evidence, not acceptance of this design.

Reuse the [kernel](../../crates/nethacked-kernel/README.md), [workflow](../../crates/nethacked-workflows/README.md), [input](../../crates/nethacked-inputs/README.md) and [timer](../../crates/nethacked-timers/README.md) contracts for authenticated calls, retained pipelines, committed prefixes and explicit services. Their present resource wiring and local scratch-state distinction require integration changes; merely renaming resources as objects is insufficient.

An owner is an independently held instance with private storage, schema, revision, module command/query implementation and invariants. It may represent one object, an aggregate, a field, a device, or another host-defined boundary. No actor, entity arena, `World`, map, mandatory mailbox, dedicated thread or clock is required. Modules can serve many instances, but each instance binds its behavior and state explicitly. Owners remain usable through their own bounded ports; coordination is opt-in.

The optional generational routing registry stores only host/owner identity, generation, live route/port, schema/code identity and lifecycle references. It holds neither authoritative property values nor a second mutable representation. Retiring/recreating an owner never reuses its identity; counters refuse before overflow. A registry handle is neither a state pointer nor authority. Grants bind actual caller, owner incarnation, named command/query, version and effective scope.

## Owner interface and derived behavior

An owner exports domain commands and queries, for example `transfer_item`, `consume_charge`, `retire_item`, `debt_summary`, or `effective_equipment`. The command defines validation, next-state construction, events and invariants; requests cannot supply replacement authoritative state. There is no generic remote `set(owner, field, value)` or guest import for slot replacement. Typed host initialization/restoration is privileged, validated and separate from public commands.

Queries return bounded detached observations with owner generation, revision, schema and relevant behavior binding. No borrowed mutable state or universal context crosses a port. Owners declare external query dependencies before preparation; hidden cross-owner reads and writes are rejected by the interface. Cross-owner invariant checks receive only declared observations and proposals, never a global state locator.

An instance binds a module artifact, command ABI/schema and ordered extension resolution. Extensions execute algorithms and can add namespaced commands or derived properties; changing constants alone is insufficient. Attach at a safe boundary to a populated owner without reconstructing it. New commands capture new bindings; pending commands retain their original executable chain, subject to fresh live authority checks. Replacement cannot silently reinterpret old tokens or state; incompatible schema changes require an explicit validated migration.

Derived properties are owner-defined queries, not authoritative duplicated fields. Each cached result carries a versioned dependency vector: owner incarnations/revisions, schema, query/extension artifacts, and applicable profile/input policy identity. A read validates that vector in a coherent view or recomputes. Equipment changes and extension replacement invalidate affected results; unrelated owner changes need not. External/time-varying inputs need recorded observations or an explicit noncacheable policy. Cross-owner caches are disposable and cannot become a second authority.

## Implementable atomic coordination

Atomicity is restricted to enrolled sealed-slot backends. An owner physically holds a private `StateSlot<T>` containing its payload and revision; distinct owners may hold unrelated `T` types in independent allocations. The wrapper permits immutable observation and pure preparation, but mutation only through the sealed publication protocol. Runtime code controls slot swaps without learning domain fields. The registry never stores these payloads. A coordinator temporarily borrows participant slot capabilities and stores bounded metadata/opaque tokens, not an authoritative resource database.

For Wasm, persistent owner state is an owner-local sealed blob with a module schema; invocation RAM is ephemeral as in the existing kernel. Pure guest preparation receives its own bounded snapshot, declared observations and command, and returns a bounded encoded candidate. Its dispatch mode permits only declared immutable observations: write ports, input sampling, scheduling and other effectful imports refuse, including through nested calls. Recorded choices must already be declared observations. The runtime seals that candidate after validation. Native typed owners can use the same slot wrapper and a private typed preparation adapter. Native backends requiring `commit()` callbacks, external I/O, arbitrary locks or mutable aliases outside the wrapper are **unsupported atomic participants** and must be refused at enrollment. Separate nontransactional ports must state their prefix semantics.

One host-local visibility gate covers every enrolled participant's authoritative reads, writes, lifecycle changes and derived-cache validation. The initial implementation may use a serialized, single-thread host executor with fallible gate entry; it requires no dedicated owner threads. A threaded backend needs equivalent exclusion and memory-ordering evidence before acceptance. Multiple coordinators cannot bypass a shared participant's gate; overlapping incompatible gate domains refuse enrollment. Cross-owner queries acquire one coherent view, not separate reads that might straddle a commit.

| Stage | Mandatory behavior |
| --- | --- |
| Declare | Bound the exact write participants and readonly observations; reject duplicates, undeclared dependencies, foreign gates and unsupported backends. Record generations/revisions, command/schema, caller, operation/phase/lease and exact module/extension resolutions. |
| Prepare | Each owner computes a pure proposed next state and opaque token bound to its slot and expected version. Run owner and declared cross-owner invariant checks over immutable observations. Preparation cannot mutate authoritative state, emit effects, perform destructive I/O or schedule callbacks. Failures abandon candidates only. |
| Seal | A nonforgeable token owns a fully constructed, validated next payload and checked next revision; guest bytes are never a commit capability. Reserve bounded token/pending storage, old-value retention, event/history storage and reply buffers. Bind exact proposed events and result. All fallible construction/encoding happens here. |
| Revalidate | At commit, enter the common gate and acquire every participant guard in canonical identity order. Recheck all live authorization, invocation/operation identity, stamps including readonly dependencies, captured executable/schema bindings, invariant evidence and capacities. Validate against the retained chain, not current future-dispatch resolution: compatible attach/detach does not invalidate a captured chain. Substituted/unavailable retained code, revoked authority or incompatible owner-state schema refuses. If invariant evidence needs rechecking, use that same retained chain and exact sealed proposal; never silently substitute a newly computed candidate. Freeze routing/grants/lifecycle changes until gate exit. |
| Publish | After every check succeeds, runtime-only sealed primitives move/swap next payload pointers and revisions into all write slots, append preallocated event output, consume the ticket and publish the transaction epoch. No guest/native owner callback, allocator, serializer, payload destructor or fallible operation runs in this interval. |
| Release | Open visibility only after the complete participant set, event prefix and consumed-ticket metadata are published. Retain old payloads and spent tokens throughout publication; release/drop them afterward outside the interval. Replies use the already staged bytes. |

Tokens and tickets are instance/transaction-bound, private and single-use; commit accepts only the issued ticket, never substituted writes/events. Failed commit validation preserves authoritative slots, revisions, history and existing pending metadata/counters. Gate entry refusal is `Busy`, never interleaved mutation. Successful preparation may consume a bounded ticket serial; abort discards only its staged candidates and never rewinds identity. Exhaustion refuses, without silent eviction.

The gate is necessary even though swapping a pointer is infallible: sequential swaps are not externally atomic without excluded readers. All authoritative ports and host inspection must obey it. Publication uses preacquired guards and preallocated retention cells; replacing an `Option`/box must move the old payload into retention rather than implicitly dropping it. Event append uses reserved storage and already encoded bytes. Unlocking cannot invoke an owner finalizer. A bypassing host pointer invalidates the guarantee.

Trust limits are explicit: native preparation purity, artifact fidelity and absence of mutable aliases need trusted adapter validation; Rust types alone do not prove capture purity. A Wasm trap, invalid candidate or checked native error before publication refuses without owner mutation. A contained native preparation panic can abort staging only if unwind safety/purity is established; otherwise poison/fail-stop the session, with no success or clean-refusal claim. Publication must contain no panic-capable guest/native work. Runtime bugs, allocator aborts and process crashes are outside in-memory atomicity; a crash between swaps is not durable atomic commit. Postpublication destructor panic/failure cannot turn a commit into refusal or replay; retain receipts and fail-stop/quarantine cleanup as supported. Durable recovery requires a separately accepted journal/codec protocol, not arbitrary rollback callbacks.

## Execution, ordering and lifecycle

Bound commands, observations, payloads, tokens, outstanding tickets, events/history, retained values/code, timers, cache entries and replies; use checked counters. Wasm fuel/memory/call depth bound guest preparation. Trusted native CPU bounds remain an explicit obligation; an elapsed timeout cannot safely preempt arbitrary Rust. Preparation cannot recursively coordinate; any reentry into a busy gate refuses. Event handlers and timer callbacks run only after visibility opens, through normal bounded commands, without replaying the publication interval.

Participant lock order is canonical identity order, not domain effect order. Events preserve declared module/profile ordering. Timer deadline units, residency and ties are profile-defined; callbacks retain owner generations, target stamps and executable bindings. A callback may schedule a later task after its command completes; recursive delivery refuses. RNG/input providers are optional recorded capabilities. Nondeterministic profiles remain permitted and declare input/ordering policies; vanilla retains its exact stream, draws, callback ties and source-derived effect order. No map/hash iteration may influence state or outputs.

Commit scope is one declared transaction, not a whole command pipeline. Earlier successful charges, choices, events or native calls are committed workflow prefixes and are never rolled back by cancellation, refusal, malformed output or a later trap. Operations authenticate tokens with the existing phase/checkpoint/lease binding; phase exit discards abandoned tokens through enrolled typed cleanup participants. Cleanup failure retains required code and a terminal operation; retry is idempotent cleanup only, never command replay.

Detach affects future dispatch while retained work keeps its code. Unload refuses while owner state/schema, tokens, derived queries, pipelines or callbacks require the artifact. Retirement validates declared item/equipment/timer/debt dependencies together, tombstones routing with a fresh generation on reuse, and invalidates caches. Serialization is owner-driven at a coherent safe boundary; the coordinator serializes metadata only. Restore validates each owner, references, identities/counters, bindings, input/timers and pending operations before complete visibility or callback scheduling. Unsupported token/backend restoration refuses explicitly; recreating stale handles or silently re-preparing old commands is forbidden.

## Retained witnesses, without a new C audit

| Witness | Autonomous behavior and invariant |
| --- | --- |
| Inventory transfer | Independent inventory aggregates and item owner prepare remove/add/location candidates from versioned capacity/quantity observations. Source ownership, destination capacity and unique item location hold together. Stale destination, unauthorized participant or refusing owner leaves all unchanged; no generic property rewrite. |
| Wand charge/debt | Reuse [authority/accounting facts](2026-10-08-authority-transaction-contract.md) and [lifetime facts](../parity/obligations/2026-10-08-p11a-lifetime-contract/README.md). Item charge/retirement, equipment and timer references, and shop ledger are distinct owners. Preserve consumed quantity, terms, creditor and liability on retirement; cleanup cannot precede accepted accounting. Respect known selected-wand committed-prefix/cancellation order rather than merging every phase into one transaction. |
| Equipment-derived properties | Equipment owns slots; items own contributions; the property module computes effective properties from stamped queries and bound extension code. Equip/retire publishes needed owners together; cache validation observes either old or new dependencies, never a mixed equipment/item view. |
| Entity-free hosts | A scalar accumulator owner plus independent device-configuration owner, and a field host with privately held field buffers, run command/query and extension behavior without entities, maps or NetHack crates. These are software witnesses, not physics claims. |

## Concrete Lean additions and obligations

The existing [Authority model](../../NetMechanics/Authority.lean) has `State.resources : Address → Option (Cell Payload)` and functional patch/publication. It proves observations and refusal/accounting laws within that model; it proves **no physical ownership**, alias exclusion, destructor safety or Rust publication refinement.

Add `NetMechanics/Ownership.lean` with heterogeneous `OwnerId → Type` payloads, `OwnerLocal`, generational `Route`, versioned `Observation`, `BehaviorBinding`, `DerivedDependencies`, opaque `PreparedToken`, `ParticipantSet` and a `PublicationPhase` transition system. Define `observeUnion` as a read-only abstraction of independently stored owner-local states; it is not a runtime shared database. Registry and coordinator types contain routing/temporary evidence only. Keep abstract ownership regions and implementation memory layouts distinct.

| Obligation | Required statement/evidence |
| --- | --- |
| Encapsulation/separation | Pairwise disjoint owner storage regions and no registry/coordinator authoritative payload alias; only sealed transitions write a region. Model this explicitly, then establish runtime representation/alias correspondence. A theorem about `observeUnion` alone cannot discharge it. |
| Preparation/behavior | Pure preparation preserves all live owner states/history; tokens target exactly one incarnation/version/binding and satisfy declared invariants. Domain command relations specify legal proposals; arbitrary `Option Payload` replacement is not sufficient. Hidden dependencies are absent. |
| Authority/refusal/replay | Adapt existing Authority caller/grant/code laws to owner routes; refused commit preserves every owner and prior event prefix. Consumed tickets cannot publish twice; stale readonly observations and generations invalidate candidates. |
| Publication/visibility | Small-step swaps touch only declared regions and preserve unrelated owners; intermediate states are unobservable while the gate is closed. Gate opening exposes the complete union and events equivalent to one abstract Authority commit. State the no-callback/no-failure publication premises and map them to sealed runtime primitives, not arbitrary owner commit laws. |
| Derived/lifecycle/composition | Valid dependency vectors yield the bound query result; invalid vectors cannot return cached authority. Retained code outlives references; retirement/reuse rejects old targets. Compose workflow committed-prefix, timer admission and restoration validity with owner publication. |

Proofs must distinguish safety assumptions from checked theorems and finite runtime bounds from unbounded Lean counters. Add command witnesses for transfer, charge/debt and derived equipment using retained facts. Machine-check proposed lemmas and publish a named Lean-to-runtime/test mapping; memory separation, native purity, Wasm isolation and crash recovery are not proved by passing Lean builds.

## Falsifiable runtime acceptance

Each acceptance fixture records initial/final owner observations, code/identity stamps and event prefixes. A centralized `Service` fixture or native-only mock cannot substitute for independent owners and guest execution.

| Test | Pass/fail criterion |
| --- | --- |
| Physical ownership | Heterogeneous independently held typed inventory/ledger owners and a Wasm blob owner share no authoritative property map. Registry inspection exposes metadata only; direct mutation/forged slot tokens are unavailable. Unsupported native commit-callback backend refuses enrollment. |
| Guest/live extension | Actual Wasm calls perform owner commands on a populated host; dynamically load executable extension code without engine rebuild, change computed behavior/add a command, preserve unrelated state. After a compatible future-dispatch replacement, a paused command must resume and commit using its retained old chain when stamps and live authority remain valid; new commands use new code. |
| Transfer/accounting | Successful inventory transfer and wand charge/retirement preserve the declared invariants across independent owners. Inject each participant's refusal and verify exact slot/history preservation; earlier accepted workflow prefixes survive later faults. |
| Identity/authority | Wrong host/caller/artifact/operation/phase/lease, revoked/narrowed grants, stale readonly/write versions, deleted/recreated owners, incompatible owner-state schema, substituted or unavailable captured code, duplicate participants and replay cannot mutate any owner or event prefix. A compatible change to future dispatch alone is not captured-code invalidation. |
| Visibility | Instrument between every internal swap: external reads, cross-owner queries and cache validation cannot see mixed states and must block/refuse while gated. After opening, all participants/events agree with one commit; unregistered bypass paths fail review. |
| Failure boundary | Guest traps, malformed candidates, native checked preparation failure, contained prepublication panic, bounds/overflow and reply/event/retention reservation failure publish nothing. Test captured reentry. Instrument publication to assert zero owner callbacks, allocations, serialization or payload drops; arbitrary native callbacks are never called as commit. |
| Postcommit faults | Commit then trap/invalid reply retains exactly one effect prefix and cannot replay. Observe old-payload destructor running only afterward; destructor panic follows documented quarantine/fail-stop policy, never clean refusal or rollback. No crash-atomicity claim from this fixture. |
| Derived/ordering | Equipment/item/extension dependency changes invalidate affected caches; unrelated changes retain valid caches. Coherent views never combine old/new stamps. Recorded nondeterministic inputs replay; vanilla draws/events/timer ties preserve established order. |
| Host/lifecycle | Scalar/device and field hosts need no entity/World/thread schema. Attach/detach/unload/retire respect live owner/token/query/timer references; cleanup refusal retains bindings and permits idempotent cleanup, never command replay. |
| Persistence | After codec acceptance, real bytes round-trip heterogeneous owner states and paused work with retained code/input/timers; restore validates before visibility/callbacks, resumes without duplicate charge, rejects stale/unsupported bindings, and exercises supported legacy NetHack migrations. |

Implementation acceptance requires focused affected checks, independent semantic review and concrete proof/test correspondence. Final code commits still require full gates/goldens. This docs-only unit runs doc-links, records raw external writer evidence and changes no source, queue, progress or proofs.
