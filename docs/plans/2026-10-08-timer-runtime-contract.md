# M4c-timer-queue: optional timers and once-only callback admission

Implement the Timer protocol in [Services.lean](../../NetMechanics/Services.lean) using accepted [callback capture/adoption](2026-10-08-callback-continuation-contract.md), [operation cleanup](2026-10-08-runtime-workflow-contract.md), and resource stamps. This closes the generic timer-runtime portion of M4c; durable restoration, vanilla scheduling/RNG adapters and NetHack domain migration remain successors.

## Schedule ownership and profile policy

Create optional `nethacked-timers`, depending on existing kernel/resources/workflows/serde libraries only. A single versioned native write endpoint handles strict tagged schedule/cancel requests. Scheduling requires a real authenticated caller and operation, exact installed service incarnation, current declared scoped write permission for the service queue resource, and authority covering every declared target address. Request data includes a bounded own-module callback export name, callback payload, target stamps, and opaque deadline/residency bytes. It contains no authoritative caller/artifact/operation/pipeline/timer identity. Callback authority is captured from a validated bounded ceiling no wider than the actual invocation. Host configuration freezes explicit typed cleanup participants; guests cannot enroll arbitrary identities.

Use `CallerView.capture_callback` during the scheduling call, after all request, target-shape, capacity/counter and reply-encoding preflight. Publish the handle and task metadata only after complete validation. The task stores non-reused service namespace/serial, exact source provenance, callback authority, target generations/revisions, profile fields and payload. Reply contains only the issued task ID. Capture failure leaves queue/counters/state unchanged; no fallible logical step follows successful capture before queue publication. A stored schedule is a committed prefix if its guest later traps. Duplicate target addresses, malformed profile data and oversize fields refuse. No mandatory entity, universal world time or RNG enters the kernel/service.

A trusted bounded profile validates opaque scheduling fields and selects an eligible pending ID from detached bounded pending metadata plus bounded host context. Selection implements due time, residency and tie ordering; profile choices need not be universally deterministic. Reject a selector result that is not currently pending. A typed target validator checks only the declared stamps against authoritative owners; no mutable World/Kernel is passed to profile or target callbacks. Profile/validation callbacks are side-effect-free, bounded, non-panicking host trust. A concrete resource-stamp adapter may use the existing resource service without copying its authority into timer state. Current target checks occur at scheduling if required by policy and always immediately before admission. No callback runs during selection/validation.

## Admission, execution and failure

Expose a trusted host boundary such as `deliver_next(&mut Kernel, context)`. Readiness, exact stored callback binding/current scheduling permission, all current stamps, request/cleanup bounds, record capacity and callback root preflight must succeed before admission. Refusal preserves queue, callback leases/identities, source/resources and history exactly. The kernel currently preflights only adopted pipelines: a minimal read-only `preflight_callback` reusing the same validation is allowed so invalid requests do not consume adoption counters. Do not duplicate routing/permission logic or recapture current dispatch.

Adopt the stored callback into a fresh operation/lease, then mark this task admitted/running before invoking code. This is the once-only admission commit point: that ID can never become pending or execute again. Callback invocation carries the new authenticated operation/checkpoint and frozen cleanup enrollment; original scheduling operation remains provenance. Cleanup all abandoned phase plans after invocation. Keep all committed resource/input/native prefixes. Root/guest trap, oversized or malformed response, unexpected post-admission error, and cleanup failure produce a terminal fault with no automatic callback retry. A bounded tagged callback response can distinguish completed versus explicit rejected result; no additional module phase graph is required for this one invocation. Store a bounded result/diagnostic. Reserve publication capacity before invocation; report pre-admission refusal separately from admitted terminal failure.

A callback must be able to schedule its next timer through the same service. Do not hold a global mutable queue borrow across guest execution or reject all legitimate scheduling reentry. Before invocation publish Running, release that borrow, and keep a bounded active-delivery guard. During it allow authenticated scheduling; refuse recursive delivery, disposal, cancellation of the running task and lifecycle mutations that could invalidate it. New schedules use their current callback invocation provenance. Other host inspection/mutation behavior must be explicit and safely borrow-checked. Trusted cleanup retry runs only idempotent participant discard, never callback code. Partial cleanup success remains retryable. Retain adopted code/participant references until cleanup succeeds and the terminal task is explicitly disposed. Dropping the original captured handle after adoption must preserve lease ownership. No universal service locator.

Pending cancellation through the native endpoint requires the same owning caller/artifact and fresh scoped service/target permissions from an authenticated operation; the original operation need not still live. Cancel only pending work, release its captured references and retain a bounded cancellation record. It runs no callback. Terminal/running cancellation and forged/foreign IDs refuse. Trusted host retirement may expose explicit pending cancellation for owner adapters with documented trust. Disposal removes only terminal tasks whose cleanup is complete, releases any adopted lease exactly once, and cannot invalidate another task's shared code. Capacity is finite and explicit; no silent eviction or ID reuse. The host must dispose finished records during long sessions.

## Required evidence

1. Real guest schedules through the native port on a populated entity-free host. Two profile fixtures demonstrate due/residency/tie-order policy (including an inactive/off-level choice); wrong/not-due selection preserves exact state. After retiring source operations, callbacks still execute. The clock/profile is optional data, not a kernel field.
2. Attach new executable callback behavior: old pending timer runs retained old code and new timer runs new code, preserving unrelated state. Live scheduling revocation/narrowing, wrong host, missing/changed target generation/revision, malformed/foreign ID and duplicate delivery refuse with otherwise valid controls. Restoring an allowed grant permits the still-pending task; changed target never becomes valid through stale handle reuse.
3. Callback schedules another timer in the same queue. Current task executes once, new task runs only in a later explicit delivery. Recursive delivery and running-task cancellation/disposal refuse; pending cancellation ownership/current-permission checks and reference release are exercised through real ports.
4. Actual callback commits a resource mutation and/or recorded input then traps or returns malformed/oversized response. Prefix survives, task is terminal, subsequent delivery cannot duplicate it. Explicit rejection also preserves prefix. Prepared but uncommitted plans are discarded; cleanup failure retains references, idempotent cleanup retry does not invoke callback and allows later disposal. Check partial participant cleanup and shared task references with exact resource/queue snapshots.
5. Admission limits, checked identity/counter exhaustion, callback-request preflight and adoption failure preserve queue/kernel/resource state before invocation. Reply-size refusal precedes capture. Test capture/drop/publication boundaries, finite terminal capacity and release failure/retry. Existing kernel/root failure conventions apply; OOM aborts and native panics remain outside the protocol.

Allowed edits: Cargo.toml/lock, new timer crate, this contract, minimal kernel preflight source/README delta plus NEW kernel test file if needed. No existing tests/helpers/assertions, resource/input/workflow production, domain or goldens. No new external dependencies; wat and existing crates may be test dependencies. If a demonstrated boundary requires broader changes, return precise evidence. Focused timer/kernel affected tests, workspace all-target Clippy for public type compatibility, fmt and actual timer/kernel wasm32 builds precede fresh semantic review and root full12/all3. Preserve commands/exits/source hashes/failure history. Document concrete Lean mapping, trusted adapters, reentrant scheduling, committed-prefix/cleanup policy and disposal duties. This is not a durable exactly-once or complete NetHack timer claim.

## M4c-timer-queue implementation mapping

The optional [timer crate](../../crates/nethacked-timers/README.md) implements this
contract with strict `Request`/`Outcome`, detached `Profile::select` plus `ready`,
current resource stamps, authenticated queue permits, captured callbacks, and
fresh one-shot adoption. `Running` publication releases the queue borrow before
invocation so real callbacks can schedule successors. All terminal outcomes keep
committed prefixes; only frozen idempotent cleanup participants retry. Hosts must
explicitly dispose finished records to release leases and bounded capacity.
This maps the Timer schedule/deliver/cancel protocol to accepted callback ownership
and workflow cleanup; persistence and NetHack scheduling adapters remain successors.
